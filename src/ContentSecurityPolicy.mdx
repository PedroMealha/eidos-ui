# Content Security Policy

A precise reference for running `eidos-ui` under a strict CSP (`style-src` without `unsafe-inline`). Short version: the compiled stylesheet needs nothing special, most components need nothing special, and a small, explicitly-named group only needs an allowance if you server-render them.

> **Note**: CSP nonces and hashes are only defined for `<style>` and `<script>` elements - never for inline `style="..."` HTML attributes on arbitrary elements. This library never generates a `<style>` or `<script>` element at runtime, so nonces are not a relevant mechanism here at all; the only lever that matters is whether `style-src-attr` allows `'unsafe-inline'`.

## The stylesheet

```css
content-security-policy: style-src 'self';
```

`eidos-ui/styles` is a single, pre-compiled, same-origin `dist/index.css` file - every colour, variant, layout rule, and keyframe animation in this library ships there. `style-src 'self'` covers all of it. No nonce, no hash, no `unsafe-inline` needed for the stylesheet under any circumstance.

## Dynamic inline styles

A handful of components set `style={{ ... }}` at runtime for values that are genuinely computed per render (a dropdown's screen position, a column's width, a picked colour) - these can't be expressed as a fixed set of CSS classes, because the value is different every time.

**For any component tree that is rendered purely on the client** (a SPA, or a React "use client" component that is never rendered to HTML on a server), none of this matters: React updates these styles through the CSSOM's per-property setters (`element.style.top = ...`, `element.style.setProperty(...)`), which CSP's `style-src`/`style-src-attr` directives do not gate at all - only the HTML `style="..."` attribute string and `.cssText`/`setAttribute('style', ...)` are gated, and this library never uses those. This is true today, with no configuration needed, verified directly against React DOM's own implementation.

**Server-side rendering** is the one case where this matters: `renderToString`/`renderToPipeableStream` serialises the `style` prop into a literal `style="..."` string in the HTML response, which _is_ markup-parsed inline-attribute usage and _is_ blocked by strict `style-src-attr`.

### Components that are always safe, including under SSR

These components render their floating surface through a portal, and a portal is client-only: the panel is created in `document.body` after the component has mounted in a browser, so its dynamic-position style cannot appear in a server-rendered payload at all.

`Combobox` · `Select` · `TagInput` (suggestions) · `Menu` · `Dropdown` · `Popover` · `ContextMenu` · `Tooltip` · `Snackbar` · `CommandPalette`

Nothing to configure for these - `style-src-attr 'self'` (i.e. no `unsafe-inline`) is sufficient.

Note that the guarantee rests on the portal boundary, **not** on the panel happening to be closed. A few of these can be open on their very first render - `Dropdown`'s `defaultOpen`, `Popover`'s `defaultOpen`/`isOpen`, `Select`'s `autoOpen`, `CommandPalette`'s `open` - and that makes no difference here: the portal is deferred until the component is running in a browser, so the server renders nothing for the panel either way.

This is re-checked on every build. Each of these components is rendered with no DOM present, open and closed, and the build fails if any of them emits a `style` attribute into the output - so the claim above cannot quietly stop being true.

### Navigation logo

`Navigation`'s brand `logo` is a different case again, worth calling out separately - it's rendered inline in the normal DOM tree (not portal-based), yet still needs no allowance under SSR, for a different reason than the components above: the exact rendered width is only ever computed and set inside the logo `<img>`'s `onLoad` handler, which is a DOM event that can only fire client-side, after the browser has decoded the image. It never runs during `renderToString`/`renderToPipeableStream`, so `Navigation`'s very first render - the one SSR captures - never includes that inline `style` at all; a fixed-height, `object-fit: contain` CSS class is the only thing present on first paint. The computed width can therefore never reach server-rendered markup, under any circumstance.

### Conversation components

`Chat`, `CommentThread` and `MessageComposer` add **no** inline-style surface whatsoever - not even under SSR. They carry no `style` prop anywhere in their source: every state they express (own vs. other message, grouped, sending, failed, entrance animation, reply indentation) is a finite set of values, so each one is a CSS class in `dist/index.css` rather than a computed style.

The one measured value they use is the composer textarea's auto-grown height, and it is set the same way `Navigation`'s logo width is: imperatively, via `element.style.height = …` inside a layout effect. That is a CSSOM per-property setter (ungated by `style-src-attr`), and a layout effect cannot run during `renderToString`/`renderToPipeableStream` - so the height can never appear in server-rendered markup. `style-src 'self'` is sufficient for these components under every rendering mode.

### Components that need an allowance only if you server-render them

These render inline in the normal DOM tree, so a server-rendered page containing them will include their computed `style` attribute in the initial HTML:

`DataGrid` (column widths, drag-row transforms) · `Table` (column widths, sticky offsets) · `VirtualList` (per-item positioning - inherent to virtualization) · `Skeleton` (custom width/height) · `Accordion` (expand/collapse height) · `ColorPicker` (computed gradient/swatch colours)

If you never server-render these specific components, they need nothing extra either. If you do, scope the allowance narrowly:

```css
Content-Security-Policy: style-src 'self'; style-src-attr 'unsafe-inline';
```

Note this only relaxes the attribute directive, not `style-src` as a whole - external stylesheets and any future `<style>`/`<script>` elements stay fully locked down.

## Theming

`ThemeProvider` needs no allowance at all, under any circumstance - including SSR. It applies a theme by calling `element.style.setProperty('--primary-color', …)` on `document.documentElement`, which is CSSOM mutation: the same mechanism described above that `style-src` and `style-src-attr` do not gate. It never creates a `<style>` element, never writes a `style` attribute, and never needs a nonce.

Under SSR the first paint uses the preset from `dist/index.css` and the theme is applied on hydration, so a non-preset theme costs one repaint. If you want a themed first paint with no repaint and no JavaScript, use `useTheme().toCss()` (or the "Copy as CSS" button in `ThemeEditor`) to generate a `:root { … }` block and paste it into your own same-origin stylesheet - which `style-src 'self'` already covers.

### The bundled fonts entry point

`eidos-ui/fonts` is the **one** part of this library that fetches a subresource. It ships `@font-face` rules for Plus Jakarta Sans and JetBrains Mono pointing at same-origin `.woff2` files, so importing it means:

```css
content-security-policy: style-src 'self'; font-src 'self';
```

`font-src 'self'` is a resource declaration, not a relaxation - unlike `style-src 'unsafe-inline'`, it grants no ability to inject anything. And if your policy sets `default-src 'self'`, **you need no new directive at all**: `font-src` falls back to `default-src` when unspecified.

This is why it is a separate entry point rather than part of `eidos-ui/styles`. Skip the import and `dist/index.css` fetches nothing whatsoever - it contains no `url()`, no `@font-face` and no `@import` - so the guarantee at the top of this page holds unconditionally for anyone who doesn't opt in.

One deployment note: bundlers emit the `.woff2` files into your own build output, which is what makes `'self'` the right origin. If you serve `dist/` directly from a CDN, the fonts come from that origin and it must be listed instead.

### Fonts you supply at runtime

`registerFontFace` (and the `ThemeEditor` upload control built on it) needs no `font-src` allowance either. It hands an `ArrayBuffer` to the CSS Font Loading API, and `font-src` governs _fetching_ a font resource by URL - there is no request to check.

It is worth being explicit that this is the **strictest** of the available options, not a shortcut around a stricter one. Registering a font can be done four ways, and they are not equivalent under CSP:

| Approach                                                     | Requires                                                  |
| ------------------------------------------------------------ | --------------------------------------------------------- |
| `new FontFace(family, arrayBuffer)` - what this library does | nothing                                                   |
| `new FontFace(family, 'url(/f.woff2)')`                      | `font-src` for that origin                                |
| A `@font-face` rule in a same-origin stylesheet              | `font-src 'self'`                                         |
| A `@font-face` rule injected at runtime in a `<style>` tag   | `font-src` **and** a nonce or `style-src 'unsafe-inline'` |
| A `@font-face` rule with a `data:` or `blob:` URL            | `font-src data:` / `font-src blob:`                       |

So a "CSS file with `@font-face`" is not more CSP-friendly than the binary form - it is strictly less so, because it reintroduces a fetch. It is still a perfectly good way to ship fonts you control (`font-src 'self'` is a mild allowance), and it is the right choice for a font your app always uses. The `ArrayBuffer` form exists for font data that arrives at runtime, where writing a stylesheet would mean either injecting a `<style>` element or encoding the font into a `data:` URL - both of which need an allowance the buffer does not.

If you fetch font files yourself before registering them, that request is your app's to declare under `connect-src`; the library never fetches a font.

## Consumer-supplied `style` props

`Input`, `Textarea`, and a few other form components accept and forward a `style` prop from your own code. If _you_ pass `style={{...}}` into one of them, that's your app's markup choice, subject to the same SSR/CSR reasoning above - it's outside this library's control either way.

## Storybook / this documentation site

Storybook's own manager UI and the `<Canvas>`/`<Controls>` blocks used throughout this documentation run on Emotion, which injects `<style data-emotion>` tags with no nonce support under the Vite-based Storybook builder - a known, still-open upstream limitation, not something fixable from this library's source. If you self-host these docs, scope `style-src 'unsafe-inline'` to that deployment specifically; it does not reflect anything about the CSP posture of the published package your app actually imports.
