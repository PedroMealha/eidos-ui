# Table

Read-only data table with sorting, pagination, column filters, custom cell rendering, and a per-row actions menu. For inline cell editing use `DataGrid` instead.

> **Note**: Table is for displaying data; DataGrid is for editing it. Read-only display: Table. Inline cell editing: DataGrid.

## Typed row data

`TableColumn<T>` checks `key` against your row type, and correlates it with the value type so `render` receives that field's own type instead of `unknown`:

```tsx
interface User {
  name: string;
  status: 'active' | 'inactive';
}

const columns: TableColumn<User>[] = [
  { key: 'name', label: 'Name' },
  // value: 'active' | 'inactive' - narrow enough to switch on directly
  { key: 'status', label: 'Status', render: (value) => <Chip>{value}</Chip> },
  // Columns that render from the whole row take a free-form key
  { key: 'actions', label: '', type: 'icon', render: (_value, item) => <Menu … /> },
];
```

`type: 'icon'`, `'action'` and `'custom'` columns address no field, so their `key` is free-form and `render` receives `undefined` as its value - use `(_, item) => …`. `'custom'` is the one to reach for when you want a computed column with normal data-cell styling.

> **Note**: an index signature on your row type switches this off - `interface User extends Record<string, unknown>` widens `keyof User` to `string`, so every key passes and every value degrades to `unknown`. Plain `interface` or `type` both work.

## Usage

```tsx
import { Table } from 'eidos-ui';
import type { TableColumn } from 'eidos-ui';

interface User {
  id: number;
  name: string;
  email: string;
}

const columns: TableColumn<User>[] = [
  { key: 'name', label: 'Name' },
  { key: 'email', label: 'Email' },
];

<Table data={users} columns={columns} />;
```

## With pagination

Enable `showPagination` and configure `pageSize` and `pageSizeOptions` to add a pagination bar below the table.

> **Note**: Table's pagination is always client-side - it slices `data` internally and has no `onPageChange`/controlled-page equivalent. If you need server-side pagination (fetching one page at a time, `totalRows` driven by the backend), use `DataGrid` instead: it supports the same client-side mode plus a server-side mode via `onPageChange` and `totalRows`.

## With filters

Set `filterable: true` and `filterType` (`'text'`, `'select'`, or `'date'`) on a column. Pass `filters` and `onFiltersChange` to control the active filter state externally.

The toolbar's filter button highlights and carries a badge with the number of applied filters, so a closed panel still makes it obvious the data is being narrowed. The count reflects _applied_ filters only - staging a filter row without clicking **Apply Filters** doesn't change it.

> **Note**: filtering in Table is always behind the toolbar's filter dropdown. There's no equivalent of `DataGrid`'s `quickFilters` - always-visible Select/Combobox/SegmentedControl filter controls in the toolbar itself. If you need a filter permanently on screen rather than one click away, use `DataGrid`.

## Row selection

Enable `selectable` to add row checkboxes, and pass `bulkActions` to expose actions over the selection. There's no "clear selection" button: the select-all control is the way out, exactly as it is in MUI or AG Grid - clicking it while it's checked deselects. In table mode that's the header checkbox; in card view (no header row) it's a **Select all** checkbox in the toolbar, which is why the toolbar is present there even before anything is selected.

`selectAllScope` decides what that control acts on: `'all'` (the default) is every row in `data`, across pages; `'page'` is only the rows currently rendered. Either way it only adds or removes the keys in its own scope, so a selection made on another page survives toggling it.

`onSelectionChange(selectedKeys, selectedRows)` gives `selectedKeys` as authoritative and `selectedRows` as best-effort - the row behind each selected key is cached, so a row still resolves after `data` has moved on. If `data` is one page of a larger set (with `totalItems` describing the whole), `selectAllScope="all"` can only reach the rows actually present, and says so with a dev-only warning.

`onSelectAllMatching` covers that case: it resolves the keys of every matching row, including ones not in `data`, and adds a **Select all N** action to the toolbar once everything the table holds is selected. It earns its keep mainly on `DataGrid`, which has a real server-side pagination mode - see [its docs](?path=/docs/data-datagrid--docs) for the full contract and a live example.

## Responsive toolbar

The toolbar wraps at every level - the row itself, both zones, and the bulk-action row - so a full toolbar (density picker, column visibility, export, filter button, and a selection count with bulk actions) can never overlap or overflow no matter how narrow its container gets. Wrapping, not shrinking, is the guarantee: `bulkActions` labels are yours, and no threshold can promise they fit.

On top of that, once the table's measured container width drops below 560px the buttons the table renders itself (Density, Columns) go icon-only with tooltips; export and the filter trigger already are. Anything you pass in is rendered exactly as given and only wraps. `DataGrid`'s toolbar behaves identically, and also stacks its `quickFilters` one per row.

## Responsive card view

`hasCardView` is on by default: the table swaps itself for a grid of cards once its own measured width (via `ResizeObserver` - not the viewport, so it responds correctly inside a narrow sidebar on an otherwise wide screen) drops to/below `cardViewBreakpoint` (default `640`), or once it can no longer fit every visible column at a 100px minimum width - whichever threshold is hit first. Set `hasCardView={false}` to always render a table. Cards themselves lay out responsively with `cardMinWidth` (default `280`) controlling how many fit per row, and each card's fields lay out in their own auto-fit grid too, so a wide card shows fields side by side instead of one per line.

Mark one column `cardHeader` and, optionally, another `cardSubheader` to use their values as the card's title/subtitle - every other column renders as a label-above-value field. A `type: 'action'` column always renders top-right of the card, and selection checkboxes top-left, regardless of where either sits in `columns`. `type: 'icon'` deliberately does not move: an icon column is as often a data glyph (a status or avatar) as it is a row-actions trigger.

Only the row rendering changes - pagination, filtering, sorting, selection and `onRowClick` all keep working exactly as in table mode, and `density` (including the `showDensity` picker) scales each card's padding and gaps the same way it scales cell padding in table mode. `draggableColumns` has no effect in card view, since there are no column headers to drag.

> **Note**: this matches `DataGrid`'s card view prop-for-prop, with the same defaults and the same measured-container logic, so the two siblings switch over at the same widths and render the same way.
