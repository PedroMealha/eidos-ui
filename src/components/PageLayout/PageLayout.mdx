# PageLayout

Application shell that composes the standard page chrome - a `Toolbar`, a `Navigation` rail, a `Header` above the page body, and a `Footer` below it - into a single grid layout. Use it as the top-level layout for an authenticated app page.

> **Note**: The navigation column is grid-`auto`-sized to `Navigation`'s own rendered width, not a fixed reservation - this is what lets `Navigation`'s own expand/collapse width transition (see its own docs) resize the whole column smoothly. Omitting `navigation` collapses the column to nothing, since there's no content to size it.

## Usage

```tsx
import { PageLayout } from 'eidos-ui';
import { LayoutDashboard, Settings } from 'lucide-react';

<PageLayout
  toolbar={{ breadcrumbs: { items: [{ label: 'Acme' }] }, userMenu: [] }}
  navigation={{
    brand: { name: 'Acme' },
    items: [
      { id: 'dashboard', label: 'Dashboard', icon: LayoutDashboard, active: true },
      { id: 'settings', label: 'Settings', icon: Settings },
    ],
  }}
  header={{ title: 'Dashboard', subtitle: 'Overview of your account' }}
  footer={{ copyright: '© 2026 Acme Inc.' }}
>
  <p>Page content goes here.</p>
</PageLayout>;
```

`footer` is optional - omit it and `PageLayout` falls back to its own `© <year> Eidos UI` notice. It accepts the same `copyright` / `component` shape as the standalone `Footer` component; `PageLayout` only applies its default top spacing to the footer region when `copyright` is used.

`navigation` is also optional and accepts the same shape as the standalone `Navigation` component - see its own docs for the brand logo, item, footer slot, and collapse behaviour. That includes `collapseBelow`, which works exactly the same way nested inside `PageLayout` as it does standalone:

```tsx
<PageLayout navigation={{ brand: { name: 'Acme' }, items: [...], collapseBelow: 1024 }}>
  ...
</PageLayout>
```

## One layout, many routes

`PageLayout` is the shell for a whole authenticated area, not for one screen. Render **exactly one instance**, in your layout/route wrapper, and never nest a second one inside a page - every page would then repeat the full navigation, toolbar and footer config, and nested child routes (`/tickets/:id`) would stack two sets of chrome.

The chrome each individual page needs (its `header`, and the leaf of the breadcrumb trail) therefore has to reach that single instance from the outside. Two sources feed it:

1. **A route table** for the static parts - title, breadcrumb parent chain, which navigation item is active. Resolve this from the current path, so the correct chrome is present on the very first paint.
2. **A context the page registers into** for the parts only the page knows - a title that depends on loaded data, an action's `loading` state, a status indicator.

```tsx
// One instance, in the layout - not in any page.
const { route } = matchRoute(path);
const pageChrome = useResolvedChrome(); // route defaults <- page overrides

<PageLayout
  navigation={{ brand, items: navItems }}
  toolbar={{ breadcrumbs: { items: breadcrumbsFor(route) }, user, userMenu }}
  header={pageChrome.header}
>
  {route.render(params)}
</PageLayout>;

// In a page - declares chrome, renders no layout.
usePageChrome(
  useMemo(
    () => ({ title: member?.name, actions: [{ children: 'Save', onClick: save }] }),
    [member, save],
  ),
);
```

The route table is what makes this pleasant: with page-registered context alone, the chrome updates one commit _after_ the page renders, so every navigation briefly shows the previous page's title. Seeding from the route and letting the page only refine it avoids that flash entirely.

A nested route group (a settings area with its own tab bar, say) needs no second `PageLayout` either - its sub-layout renders the tabs plus the active child, and nothing else.

> **Note**: `header` is a data prop, not a slot, so there is nothing to portal JSX into - a page's header content must travel as data (as above) rather than as rendered elements.

## Scrolling

The `main` content area is the layout's only scroll region. The toolbar and navigation rail stay fixed; the header, page body and footer all scroll together inside it, each sized to its own content. Nothing is pinned - if you want a header that stays visible, add `position: sticky; top: 0` to it yourself.

`PageLayout` therefore fills its container rather than growing with its content, so give it a bounded height - a parent with a real height, or `100vh`/`100dvh` at the app root. Dropping it into an unbounded page will make it collapse to its minimum height instead.

When the page content is shorter than the scroll region, the body absorbs the leftover space, so the footer sits on the bottom edge rather than floating up under the content.

## The page gutter

The toolbar, header, body and footer share one left/right inset, so everything on the page sits on the same two vertical edges. It steps down with the viewport - 3rem, then 1.5rem below `xl`, 1rem below `lg`, 0.5rem below `md`.

It is expressed in `rem` rather than the `--spacing-*` tokens on purpose. Those are `em`, so they resolve against each region's own font-size: the footer renders at `--font-size-sm`, which made the same token 36.75px there against the body's 42px, and the two regions drifted apart. A page gutter has to be one distance, not a multiple of whatever text a region happens to contain.

The practical consequence for custom content: **give a custom `footer.component` vertical padding only.** The region already carries the horizontal inset, so adding your own would indent the content twice and pull it out of line with the page above.

## Responsive behaviour

Every piece of `PageLayout`'s chrome adapts on its own, with no coordination required between them - though they don't all measure the same thing, which matters here specifically because the navigation rail makes the content column narrower than the window:

- **`Navigation`** can auto-collapse to icon-only via `navigation.collapseBelow` (or be driven manually/externally - see its own docs) - the grid column narrows smoothly along with it, since that column is sized to `Navigation`'s own rendered width rather than a fixed reservation (see the note above). This one is keyed off the **viewport**, via `window.matchMedia`.
- **`Toolbar`** wraps its breadcrumb trail onto its own line rather than clipping it or squeezing the search/actions/user menu aside, once there isn't room for both on one line. Pure CSS wrapping, no breakpoint.
- **`Header`** is keyed off **its own width**, not the viewport - which is what makes it correct inside this layout, where its column is the window minus a rail that is itself collapsible. At 640px of header width it stacks the actions below the title stack, stretches them to fill the line, and folds everything past the first into an overflow popover. See the `Header` docs for the full ladder.

Because of that last point, a 800px window with an expanded rail gives `Header` roughly 610px to work with, and it reflows to its narrow layout even though the window is nowhere near 640px. That is deliberate, and it is the behaviour a viewport breakpoint gets wrong.

## An identity page

An account or profile screen gets the same treatment `IdentityHeader` provides - but note what is being passed. `header` is a data prop, so the `IdentityHeader` **component** cannot go here; `PageLayout` always renders a `Header`. The shape travels as data instead, because `media`, `meta` and `variant` live on `Header` itself rather than only inside the preset:

```tsx
<PageLayout
  header={{
    variant: 'hero',
    title: 'Ana Ferreira',
    subtitle: 'Customer Support · Lisbon',
    media: <Avatar name="Ana Ferreira" size="lg" color="primary" />,
    meta: [{ label: 'Role', value: 'Admin', icon: 'shield' }],
  }}
>
  ...
</PageLayout>
```

The only thing `IdentityHeader` adds over this is its `avatar` shorthand. Reach for the component directly when a page renders its own header rather than feeding a shared layout.

## Without a navigation rail

`navigation` is optional, and omitting it collapses the rail's column to nothing rather than leaving an empty gutter - the column is sized to `Navigation`'s own rendered width, so with no content there is no width. The toolbar then spans the full layout.

## Custom footer

`footer` is a discriminated union - pass `copyright` for the default centered notice or `component` to replace it entirely. `PageLayout` applies its own vertical footer spacing only to the `copyright` variant, so a custom component owns its own padding.
