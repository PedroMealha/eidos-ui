# DataGrid

A feature-rich, spreadsheet-like grid for editing structured data inline. Columns are typed (`text`, `number`, `select`, `checkbox`, `readonly`, `actions`), and the grid supports sorting, filtering, pagination, row selection, drag-and-drop reordering, column pinning, per-cell validation, a row-actions menu, and a responsive card view for narrow containers - all opt-in via props.

> **Note**: `DataGrid` is generic over your row type (`T extends Record<string, unknown>`). Pass the type parameter explicitly - e.g. `<DataGrid<Person> … />` - to get full type safety on `columns`, `onChange`, and callbacks.

## Usage

```tsx
import { DataGrid } from 'eidos-ui';
import type { DataGridColumn } from 'eidos-ui';

interface Person extends Record<string, unknown> {
  id: number;
  name: string;
  role: string;
}

const columns: DataGridColumn<Person>[] = [
  { key: 'id', header: 'ID', type: 'readonly', width: 60 },
  { key: 'name', header: 'Name', type: 'text', minWidth: 160, required: true },
  {
    key: 'role',
    header: 'Role',
    type: 'select',
    width: 130,
    options: [
      { value: 'lead', label: 'Lead' },
      { value: 'senior', label: 'Senior' },
    ],
  },
];

function TeamTable() {
  const [data, setData] = useState<Person[]>([{ id: 1, name: 'Alice', role: 'lead' }]);

  return <DataGrid<Person> columns={columns} data={data} rowKey="id" onChange={setData} />;
}
```

## With filtering

Filterable fields live in their own dedicated `filterConfig` array - `{ key, label, filterType, filterOptions, dateFilterMode }` - kept separate from `columns` so every filterable field is visible in one place, instead of scattered across each column's own definition. `key` doesn't need to match a `columns` entry either - you can filter on any row-data field, including ones you don't render as a column.

Pass `filterConfig` alongside `showFilters={true}` to show the filter-panel toggle in the toolbar. Without `onFiltersChange` the grid filters client-side.

For `filterType: 'date'` fields, `dateFilterMode` (`'single' | 'multiple' | 'range'`, same shape as `TableColumn`) controls which date-picker mode the filter dropdown uses - it defaults to `'single'` if omitted.

The toolbar's filter button highlights and carries a badge with the number of applied filters, so it's clear at a glance that a filter is narrowing the data while the panel is closed. The count reflects _applied_ filters only - staging a filter row without clicking **Apply Filters** doesn't change it.

## With quick filters

`quickFilters` renders always-visible filter controls on the left of the toolbar, for the one or two filters users reach for constantly rather than ones they open a panel for. There's no `showFilters`-style flag - a non-empty array is what enables them. Each entry is discriminated on `type`, so it only accepts the props that apply to that control:

| `type`        | Renders            | Type-specific props                                                                      |
| ------------- | ------------------ | ---------------------------------------------------------------------------------------- |
| `'select'`    | `Select`           | `options`, `multiple`, `clearable`, `placeholder`                                        |
| `'combobox'`  | `Combobox`         | `options`, `placeholder`, `clearable`, `emptyText`, `onSearch`, `loading`, `loadingText` |
| `'segmented'` | `SegmentedControl` | `options`, `color`, `allLabel`                                                           |

All three also take `key`, `label`, `disabled`, `width`, and `defaultValue`. Only sizing is configurable - `size`, `fullWidth`, and `className` are fixed by the grid so every quick filter matches the rest of the toolbar. Option objects are the underlying components' own option types minus `id` (the grid fills that in from `value`), so a `'segmented'` filter still supports per-segment `icon`/`tooltip`, and a `'combobox'` one still supports `description`/`group`.

```tsx
<DataGrid<Person>
  columns={columns}
  data={data}
  quickFilters={[
    {
      type: 'segmented',
      key: 'department',
      label: 'Department',
      options: [
        { value: 'engineering', label: 'Engineering' },
        { value: 'design', label: 'Design' },
      ],
    },
    { type: 'select', key: 'role', label: 'Role', multiple: true, options: roleOptions },
  ]}
/>
```

A `'segmented'` filter always gets an extra reset segment prepended, ahead of the options you pass - a `SegmentedControl` always has exactly one segment selected, so without it the filter could never be cleared. It reads `All` by default; rename it with `allLabel`. Select and combobox filters need no equivalent because `clearable` (on by default) already gives them an empty state.

> **Note**: `defaultValue` applies only when the grid manages filter state itself. In server-side mode (`onFiltersChange` set) the caller owns `filters`, so seed your own initial state instead.

### How quick filters and the filter dropdown interact

Both write to the same filter state, which means they compose - a quick filter and a dropdown filter narrow the data together - and server-side mode still receives everything through one `onFiltersChange` object. Each side owns a distinct set of keys:

- A `key` claimed by a `quickFilters` entry **wins and is dropped from the dropdown**, so the same field is never editable from two controls at once. Keep the two key sets distinct unless that's what you want.
- The dropdown's **Clear All** clears only the dropdown's own filters; the quick filters keep their values. The "no results found" empty state's **Clear filters** resets everything.
- The filter button's badge counts the dropdown's own filters only. Quick filters are already visible with their state on show, and the badge exists to surface what a _closed_ panel is hiding - counting them would also imply the dropdown's **Clear All** would reset them, which it doesn't.

Quick filters are hidden while rows are selected - the selection count and bulk actions take over the same toolbar zone.

## With selection

Enable `selectable={true}` to add row checkboxes. Nothing is rendered by default - pass a `bulkActions` array to expose actions, each fully under your control (`id`, `label`, `icon`, `color`, `variant`, `disabled`). Each action's `onClick` receives the full array of selected row objects.

Set `type: 'split-button'` (default is `'button'`) to render a primary action plus a dropdown of secondary `options`, instead of a plain button. Omit `label` on a `'button'` action to render an icon-only button.

## Column alignment

Set `align` to `'left'` (default), `'center'` or `'right'` on a column - the same values as `TableColumn.align` - to align its header and cell content together. Typically `'right'` for numeric columns. On a sortable column the sort icon follows the alignment instead of staying pinned to the far edge.

> **Note**: alignment applies in table mode only. Card view renders each field as a label above its value, where aligning the value away from its own label reads as a misalignment rather than a choice.

## Pinned columns

Columns with `pin: 'left'` or `pin: 'right'` stay frozen during horizontal scroll. The grid reorders them to the correct edge regardless of where they appear in the `columns` array.

## Row actions menu

Give a column `type: 'actions'` and an `actions` array to render a "more" (⋮) trigger instead of a data value - clicking it opens a menu built from that array (`label`, `icon`, `onClick(row, index)`, and optionally `disabled` - a boolean or a `(row) => boolean` predicate, `danger` for destructive styling, and `divider` to place a separator directly above that item). Only one column may set `type: 'actions'`; it's always rendered at the far right in table mode regardless of its position in `columns`, and top-right of the card in card view (see below). The trigger icon defaults to a vertical 3-dot icon, overridable via `actionsIcon`.

> **Note**: there's no `onRowDelete` prop - deleting a row (or any other destructive action) is just an `actions` entry whose `onClick` updates your own data/state, same as any other action.

<Canvas of={DataGridStories.RowActionsMenu} />

For menu capabilities `actions` can't express - nested submenus, custom `component` content, or keyboard `shortcut` labels - set `renderActions: (row, index) => MenuItemType[]` on the same column instead of `actions` (it takes precedence when both are set). `MenuItemType` is the exact type the standalone `Menu` component takes, so anything `Menu` supports is available here too.

## Responsive card view

`hasCardView` is on by default: the grid swaps the table for a grid of cards once its own measured width (via `ResizeObserver` - not the viewport, so it responds correctly inside a narrow sidebar on an otherwise wide screen) drops to/below `cardViewBreakpoint` (default `640`), or once it can no longer fit every column at a 100px minimum width - whichever threshold is hit first. That second condition means a wide, many-column grid never has to overflow horizontally waiting for a hand-tuned `cardViewBreakpoint`. Set `hasCardView={false}` to always render a table. Cards themselves lay out responsively with `cardMinWidth` (default `280`) controlling how many fit per row, and each card's fields lay out in their own auto-fit grid too, so a wide card shows fields side by side instead of one per line.

Mark one column `cardHeader` and, optionally, another `cardSubheader` to use their values as the card's title/subtitle - every other column renders as a label-above-value field. The row-actions column (see above) always renders top-right of the card, and selection checkboxes top-left, regardless of where either sits in `columns`.

Only the row rendering changes - pagination, filtering, sorting, selection, and inline cell editing all keep working exactly as in table mode. `draggableRows` is not available in card view.

## Expandable rows

Set `expandable` and `renderExpandedContent: (row, index) => ReactNode` to add a chevron that reveals extra per-row content - a dedicated column in table mode, a toolbar toggle in card mode. `renderExpandedContent` is genuinely lazy: it only runs the first time a given row is actually opened, so it's safe to kick off a data fetch from it without worrying about firing for every row up front. The open/close transition mirrors `Accordion`'s own max-height animation for a consistent feel.

By default (`expandMultiple`, default `true`) any number of rows can be open at once; set it to `false` for accordion behaviour, where opening a row auto-collapses whichever other row was open. Use `isRowExpandable: (row) => boolean` to omit the chevron/toggle entirely for rows that shouldn't be expandable. Expansion state works exactly like selection - uncontrolled by default, or controlled via `expandedRows`/`onExpandedRowsChange` (with `defaultExpandedRows` for an uncontrolled initial value).
