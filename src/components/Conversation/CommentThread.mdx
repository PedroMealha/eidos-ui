# CommentThread

A comment section for a discussion between several people. Unlike `Chat` it has no scroll region of its own - it grows down the page in normal document flow, supports one level of replies, and pages _downward_.

> **Note**: `CommentThread` and `Chat` share one message model, so the same stored history renders in either. Choose `CommentThread` when comments sit inside a longer page; choose `Chat` when the conversation owns a fixed-height panel and should stay pinned to the newest message.

## Usage

```tsx
import { CommentThread } from 'eidos-ui';

const comments = [
  {
    id: 'c-1',
    author: { id: 'u-3', name: 'Chiara Ricci', role: 'Admin' },
    body: 'Proposing we drop the legacy v1 endpoint in the next major.',
    sentAt: '2026-09-17T11:02:00.000Z',
  },
];

<CommentThread
  title="Discussion"
  messages={comments}
  currentUserId="u-1"
  onSend={async (draft) => {
    await api.comment(draft.body);
  }}
/>;
```

## The message model

Identical to `Chat`'s - see the [Chat docs](?path=/docs/data-chat--docs) for the full shape. It is deliberately free of React nodes and functions so a thread can be persisted and replayed verbatim; use `renderBody` for markdown or rich text rather than putting elements in the data.

## Ordering and composer placement

Top-level comments follow `order`; replies always read oldest-first, since a conversation under a single comment is chronological by nature.

## Permissions

There is no `permissions` object. Capability is expressed by the props you supply:

| Capability                 | How                                                 |
| -------------------------- | --------------------------------------------------- |
| Post at all                | `readOnly`, or omit `onSend`                        |
| Reply                      | omit `onReply`                                      |
| Act on **a given** comment | `messageActions(message)` - return `[]` for no menu |
| Attach files               | `allowAttachments`                                  |

`readOnly` **removes** the composer rather than disabling it, and `readOnlyMessage` explains the absence so it is not silent.

> **This is a UI affordance, not authorization.** Removing a composer does not stop anyone POSTing to your API. Enforce permissions on the server; use these props to avoid showing people controls that would fail.

## Responsive behaviour

Layout responds to the component's own width via container queries, so a thread in a narrow sidebar collapses correctly on a wide screen. Below the `sm` breakpoint reply indentation drops to a thin rule and the composer actions stack.

## Motion

New comments fade and rise 4px into place; comments present on the first render never animate. The animation is `opacity` and `transform` only, is disabled under `prefers-reduced-motion: reduce`, and can be turned off with `animateNewMessages={false}`.

## Paging

`onLoadMore` renders a load-more control below the thread. There is no scroll container, so unlike `Chat` there is no scroll-triggered fetch - the reader asks explicitly.

<Canvas of={CommentThreadStories.WithLoadMore} />

Comments are **not virtualized**: everything in `messages` is in the DOM. Page long threads rather than passing all of them at once.

## Reactions and extra metadata

Reactions are not built in - a useful implementation needs an emoji picker and a reaction store, both of which belong to your app. `renderMessageFooter` is the extension point.

<Canvas of={CommentThreadStories.WithMessageFooter} />

The same applies to edit and delete: `messageActions` supplies the menu items, and your app owns the confirmation and the mutation. `edited` on a message renders the marker.

## Replies

Supplying `onReply` enables a Reply control on each comment and an inline composer beneath it. The emitted draft carries `parentId`.

<Canvas of={CommentThreadStories.WithReplies} />

> **Nesting is one level deep, by design.** A reply to a reply is flattened onto the same level as its parent and labelled "Replying to …", rather than indenting further. Deeper indentation leaves almost no width for text on a phone, which is why GitHub and Linear do the same. Nothing is discarded - a `parentId` pointing at a message that is not loaded is treated as top-level, so a paged-out or deleted parent never makes a reply disappear.
